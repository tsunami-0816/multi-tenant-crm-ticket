## 2. 整体分层架构

```
┌─────────────────────────────────────────────────┐
│  接入层  Vue3 前端 (Vite Dev / Nginx 静态)       │
└──────────────────┬──────────────────────────────┘
                   │ HTTPS/HTTP
┌──────────────────▼──────────────────────────────┐
│  网关层  gateway-service (Spring Cloud Gateway)  │
│         · 路由转发                                │
│         · JWT 鉴权                                │
│         · 租户上下文解析 (X-Tenant-Id)            │
│         · 全局 CORS / 异常处理                    │
└──────────┬───────────────────────┬──────────────┘
           │                       │
┌──────────▼──────────┐  ┌─────────▼─────────────┐
│  服务层              │  │                       │
│  customer-service   │  │  ticket-service       │
│  · 客户 CRUD         │  │  · 工单 CRUD          │
│  · 跟进记录          │  │  · 工单状态机          │
│  · 客户时间线查询     │  │  · 本地消息表           │
│  · Redis 缓存        │  │  · Kafka Producer      │
│  · Kafka Consumer   │  │                       │
└──────┬───────┬───────┘  └─────────┬─────────────┘
       │       │                    │
┌───────▼──┐ ┌─▼──────┐  ┌─────────▼─────────┐
│ 存储层   │ │        │  │                   │
│ MySQL   │ │ Redis  │  │  Kafka 3.6        │
│ (业务库) │ │ (缓存) │  │  (事件流)          │
└─────────┘ └────────┘  └───────────────────┘

┌─────────────────────────────────────────────────┐
│  运维层  Nacos (注册+配置) / Docker Compose       │
│         Spring Boot Actuator / Logback           │
└─────────────────────────────────────────────────┘
```

**各层职责**：
- 接入层：浏览器 SPA，只做页面渲染和表单提交
- 网关层：统一入口，鉴权和租户上下文在这一层做，下游服务不重复校验
- 服务层：业务逻辑，每个服务独立数据库 schema（MVP 阶段共用一个 MySQL 实例，不同 database）
- 存储层：MySQL 持久化、Redis 缓存、Kafka 事件流
- 运维层：Nacos 注册配置、容器编排、Actuator 健康检查、日志

## 3. 核心业务链路

### 链路 1：租户注册与登录

```
前端 POST /api/auth/register {companyName, username, password, role}
  → gateway-service
    → customer-service /auth/register
      → MySQL: insert tenant + user
      → 返回 tenantId
前端 POST /api/auth/login {username, password}
  → gateway-service
    → customer-service /auth/login
      → MySQL: 查 user + tenant
      → 签发 JWT (含 userId, tenantId, role)
      → 返回 {token, userInfo}
前端后续请求 Header: Authorization: Bearer <token>, X-Tenant-Id: <tenantId>
  → gateway 校验 JWT → 解析 tenantId → 透传给下游
```

### 链路 2：客户 CRUD（含 Redis 缓存）

```
GET /api/customers?page=1&size=20
  → gateway → customer-service
    → MyBatis-Plus 多租户拦截器自动拼 WHERE tenant_id = ?
    → 直接查 MySQL（列表页不缓存）

GET /api/customers/{id}
  → gateway → customer-service
    → 查 Redis: customer:{tenantId}:{id}
      命中 → 直接返回
      未命中 → 布隆过滤器判断 ID 是否存在
        不存在 → 返回 404
        存在 → Redis 分布式锁(lock:customer:{id})
          只放一个请求回源 MySQL
          回源后写 Redis，TTL = 30min + random(0~5min)
PUT /api/customers/{id}
  → gateway → customer-service
    → 更新 MySQL
    → 延迟 500ms 后删除 Redis key (延迟双删)
```

### 链路 3：工单状态机 + Kafka 事件流

```
POST /api/tickets {customerId, title, description}
  → gateway → ticket-service
    → @Transactional: insert ticket (status=OPEN)
    → 事务提交后 afterCommit() 回调：
        立即 send Kafka topic=ticket.status.changed
        成功 → 流程结束
        失败 → insert local_message (status=0 待补发)
PATCH /api/tickets/{id} {status: PROCESSING}
  → gateway → ticket-service
    → 状态机校验: OPEN→PROCESSING 合法, 已关闭的拒绝
    → @Transactional: update MySQL
    → afterCommit() 回调立即发 Kafka，失败落 local_message
local_message 补发: 定时任务 fixedDelay=5s 扫 status=0 的记录，重试发送
Kafka topic: ticket.status.changed
  → customer-service @KafkaListener
    → 幂等校验: 查 customer_timeline 表是否已有 event_id
      已有 → ack 跳过
      没有 → insert customer_timeline (聚合客户时间线)
      失败 3 次 → 进 DLQ topic
```

> **设计说明**：正常路径走"事务提交后立即发送"，端到端延迟 = 业务事务 + Kafka 生产，P99 ≤ 2s 可达成；只有发送失败才落 local_message 走定时补发，兜底方案。

### 链路 4：客户详情时间线聚合

```
GET /api/customers/{id}/timeline?page=1&size=20
  → gateway → customer-service
    → 应用层聚合分页：
      1. 分别查 customer_follow 最近 50 条 + customer_timeline 最近 50 条（各自带 tenant_id 条件）
      2. 内存合并、按 occurred_at DESC 排序
      3. 内存分页取当前页
    → 返回
```

> **设计说明**：不用 SQL UNION 分页（复杂且慢），应用层聚合在数据量 ≤ 100 条/客户时足够快，避免跨表分页问题。

**多租户约束（强制）**：
- MyBatis-Plus 多租户插件自动拼接 tenant_id 条件，但只对 MP 自动 CRUD 和注解 SQL 生效
- XML 手写 SQL 必须**显式**写 `WHERE tenant_id = #{tenantId}`，禁止漏写
- L3 集成测试强制覆盖"手写 SQL 查询也做租户隔离"场景，CI 跑

## 5. 接口规范定义

### 5.1 统一返回格式

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

错误码规范：
- `0` 成功
- `40001` 未登录 / token 过期
- `40003` 无权限（角色不匹配）
- `40401` 客户不存在
- `40402` 工单不存在
- `40901` 工单状态机非法流转
- `500xx` 服务端错误

### 5.2 鉴权规则

- 除 `/api/auth/**` 外所有接口必须带 `Authorization: Bearer <JWT>`
- JWT access token 有效期 2h，签名用 HS256
- 用户密码 BCrypt 加密，strength = 10
- 网关校验 JWT 签名和有效期，解析出 `userId`、`tenantId`、`role`，透传 Header：
  - `X-User-Id`
  - `X-Tenant-Id`
  - `X-User-Role`
- 下游服务信任网关透传的 Header，不再解析 JWT
- MyBatis-Plus 多租户插件从 `X-Tenant-Id` 读当前租户，自动拼条件
- 登出：token 存入 Redis 黑名单，TTL = token 剩余有效期

### 5.3 核心接口清单

| Method | Path | 说明 | 归属服务 |
|---|---|---|---|
| POST | /api/auth/register | 租户+用户注册 | customer |
| POST | /api/auth/login | 登录发 JWT | customer |
| POST | /api/auth/logout | 登出（token 加 Redis 黑名单） | customer |
| GET | /api/customers | 客户列表（分页） | customer |
| POST | /api/customers | 新建客户 | customer |
| GET | /api/customers/{id} | 客户详情（走缓存） | customer |
| PUT | /api/customers/{id} | 更新客户（延迟双删） | customer |
| GET | /api/customers/{id}/timeline | 客户时间线（应用层分页） | customer |
| POST | /api/customers/{id}/follows | 新增跟进记录 | customer |

## 6. 部署架构设计

### 6.1 Docker Compose 服务清单（8 个容器）

| 容器 | 镜像 | 端口 | 内存限制 |
|---|---|---|---|
| mysql | mysql:8.0 | 3306 | 1GB |
| redis | redis:7.2 | **6380**（避开已有 rag-redis 的 6379） | 256MB |
| kafka | apache/kafka:3.6 | 9092 | 1GB |
| nacos | nacos/nacos-server:v2.3.0 | 8848 | 512MB |
| gateway | 本地构建 | 8080 | 512MB |
| customer-service | 本地构建 | 8081 | 512MB |
| ticket-service | 本地构建 | 8082 | 512MB |
| frontend | nginx 托管 dist | 80 | 64MB |

总计约 4.9GB 内存，16GB 机器充裕。

**健康检查**：
- MySQL: `mysqladmin ping -h localhost`
- Redis: `redis-cli ping`
- Kafka: `kafka-broker-api-versions --bootstrap-server localhost:9092`
- Nacos: `curl -f http://localhost:8848/nacos/v1/console/health/readiness`
- 后端三个服务: `curl -f http://localhost:<port>/actuator/health`
- 前端: `curl -f http://localhost/`

### 6.2 环境划分

MVP 只有一套本地环境，`.env` 管理配置。生产环境不部署（个人项目），但 README 里写清楚迁移到生产需要改什么。

### 6.3 高可用方案（MVP 务实版）

- Redis：缓存挂了直接回源 DB，不熔断（`fallback`）
- Kafka：消费失败进 DLQ，不阻塞主流程
- Nacos：单机挂了服务间调用失败，重启 Nacos 恢复（MVP 接受）
- MySQL：单点，不做主从

## 7. 监控与运维（MVP 务实版）

不上 Prometheus/Grafana，MVP 用最简单的：
- **健康检查**：Spring Boot Actuator `/actuator/health`，Docker healthcheck
- **日志**：Logback 输出到文件，按天滚动；ERROR 级别单独文件
- **业务指标**：JMeter 压测时手动看 QPS/RT；埋点日志里打 `CACHE_HIT`/`CACHE_MISS`/`KAFKA_CONSUME_SUCCESS`/`KAFKA_CONSUME_FAIL`
- **运维操作**：README 写 `docker compose logs <service>` / `docker compose restart <service>` 常用命令

## 8. 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Spring Cloud Alibaba 版本对应错 | 启动报错 | 已锁定 2023.0.1.2 ↔ Spring Boot 3.2.5，step03 用 dependency_checker.py 校验 |
| Windows Docker 里 Kafka 性能差 | 压测数据不好看 | 诚实报告，README 说明"本地开发环境数据，生产调优另说" |
| 多租户拦截器漏过滤（某条 SQL 没拼 tenant_id） | 数据越权 | L3 集成测试强制写"租户 A 查不到租户 B"用例，CI 跑 |
| Redis 缓存与 DB 双写不一致 | 客户详情显示旧数据 | 延迟双删 + 压测验证不一致窗口 < 1s |
| Kafka 重复消费导致工单状态回退 | 业务数据错乱 | 消费端 event_id 唯一索引 + 状态机校验 |
| 本地 16GB 内存跑 8 容器不够 | OOM | 每个容器设 memory limit，总计 ≤ 5GB |
| 用户对 Spring Cloud/Kafka 不熟 | 开发卡住 | 用 Codex/Cursor 辅助，但 step04 任务拆解要把每个模块拆到小时级 |
